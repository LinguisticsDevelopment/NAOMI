================================================================================
PART A -- LOSS-FUNCTION CODE REVIEW
(src/nsm_ct/encoder_model.py: linearize_tree, legal_action_types,
teacher_force_loss; scripts/train_encoder.py's minibatch loop)
================================================================================

1. Action-type CE (encoder_model.py:529-533)
   target = ACTION_INDEX[step.action] (the GOLD action), scored against
   type_logits = action_type_head(h) + mask, mask built from
   legal_action_types(open_clause, i, T, has_clause) using the PRE-step
   state. CLEAN. Traced every state legal_action_types can be called in
   against every step linearize_tree can emit (initial OPEN_CLAUSE-only
   state; open-clause interior SHIFT/GROUND/EMIT_*/CLOSE_CLAUSE; the
   has_clause-gated post-close flush SHIFT/OPEN_CLAUSE/STOP) -- could not
   construct a gold step the mask excludes. This matches the module's own
   "verified by construction" docstring claim (lines 372-381) and is
   corroborated empirically: Part B below measures STOP accuracy = 1.0000
   and finite (non-NaN/inf) loss throughout the historical training run's
   own loss_curve, exactly what you'd see if no masked gold target (which
   would CE against a -inf logit -> +inf loss) ever occurred.

2. Terminal-weight class weighting (encoder_model.py:496-502, 521, 533)
   `_action_type_class_weights` builds a length-8 weight vector matching
   ACTION_TYPES' own order, setting only CLOSE_CLAUSE (index 6) and STOP
   (index 7) to `terminal_weight`, passed as F.cross_entropy's per-class
   `weight=`. CLEAN. Indices verified against ACTION_TYPES; only the
   action-type CE is reweighted, no other term touched, exactly as the
   docstring claims.

3. Role CE (encoder_model.py:545-548)
   Fires for action in (GROUND, ATTACH, EMIT_SYNTH_SLOT,
   EMIT_UNRESOLVED_SLOT), target = model.role_id(step.role). `step.role` is
   populated for all of these in linearize_tree via clause_node_order's
   role name. CLEAN. Side note (not a bug): ATTACH is dead code -- the
   oracle (linearize_tree) never emits it, and legal_action_types never
   makes it legal at any state, so its branch in teacher_force_loss and in
   the ACTION_TYPES list is presently unreachable. Confirmed empirically in
   Part B: ATTACH support = 0.

4. Grounding-type CE (encoder_model.py:549-552)
   Fires exactly when action in (GROUND, EMIT_SYNTH_SLOT,
   EMIT_UNRESOLVED_SLOT) and step.gtype is not None, target =
   GTYPE_INDEX[step.gtype]. This lines up exactly with which actions carry
   a gtype in linearize_tree (GROUND: sense/entity; EMIT_SYNTH_SLOT: prime;
   EMIT_UNRESOLVED_SLOT: reference/elision). CLEAN.

5. Source CE (encoder_model.py:553-556)
   Gate is `step.gtype in ("sense","reference","elision")` -- keyed on
   GTYPE, not action -- deliberately excluding "entity" and "prime"
   groundings from a source target (those aren't retrieval-sourced).
   CLEAN, and verified CONSISTENT with decode: `_apply_action`'s own gate
   for computing a source prediction at decode time (encoder_model.py:828,
   `if gtype in ("sense","reference","elision")`) uses the identical
   three-way set. Train and decode agree on exactly which nodes get a
   source head at all.

6. Prime CE (encoder_model.py:557-560)
   Fires only for EMIT_SYNTH_SLOT with step.prime is not None, target
   PRIME_INDEX.get(step.prime, PRIME_INDEX["<UNK_PRIME>"]). CLEAN.

7. Buffer-pointer advance / teacher forcing of the NEXT step's input
   (encoder_model.py:562-563, and the whole step loop's state block)
   `i = step.token_index + 1` fires for SHIFT/GROUND/EMIT_UNRESOLVED_SLOT,
   mirroring linearize_tree's own i-updates for exactly those three actions
   (shift_to's `i += 1` loop for SHIFT; `i = eff_tidx + 1` at lines 318 and
   328 for GROUND/EMIT_UNRESOLVED_SLOT). EMIT_SYNTH_SLOT (prime) correctly
   does NOT advance i, matching the oracle (a prime slot consumes no
   token). CLEAN. More generally: EVERY state variable that conditions the
   next step (open_clause, open_kind_id, has_clause, i, prev_action_id) is
   updated from the GOLD `step` at every iteration in teacher_force_loss --
   the model's own head outputs are used ONLY to compute that step's loss
   and never fed back into the recurrent state. This is exact, leak-free
   teacher forcing (never the model's own prediction), confirmed by
   reading the full loop body top to bottom.

8. Mask consistency between train and decode
   Both teacher_force_loss and beam_decode call the SAME
   `legal_action_types` / `_mask_vector` functions (encoder_model.py:
   348-401) with the same state convention (open_clause, i, T, has_clause).
   The only difference is WHERE the state comes from: the gold step
   (train) vs. the beam's own prior action (decode) -- exactly the intended
   train/decode distinction, not a drift bug. CLEAN.

9. Double-counting / mis-indexing / dropped terms
   Traced the full per-step body: the 6 heads (action-type, kind, role,
   gtype, source, prime) are gated by mutually-exclusive, non-overlapping
   per-action/per-gtype conditions -- no term is computed twice for one
   step, and none of the conditions silently skip a term linearize_tree
   actually populates for that action. CLEAN.

10. Minibatch/gradient-accumulation loop (scripts/train_encoder.py:164-190)
    `loss = teacher_force_loss(...) / batch_size`, then `.backward()` is
    called once per derivation and accumulated; `opt.step()` fires every
    `batch_size` derivations AND once more at end-of-epoch for the
    remainder. NOT A BUG, but a minor, common convention worth flagging:
    when `len(train_items) % batch_size != 0`, the final partial batch of
    an epoch still divides by the FULL `batch_size` rather than its own
    (smaller) size, so its per-example gradient contribution is slightly
    diluted relative to full batches. No gold target is dropped or
    misweighted by this -- it only very slightly under-weights the last
    partial batch's average gradient magnitude each epoch. Negligible at
    n_train=788, batch_size=32 (one ~20-item remainder batch out of ~25
    per epoch); does not explain or relate to any decode-time symptom.

11. "Is a gold target ever masked to -inf?"
    No instance found by construction-tracing (item 1) or by the empirical
    checks in Part B (STOP=1.0000 accuracy; CLOSE_CLAUSE=0.8155, both
    comfortably learned, not floor-level/random -- which is what a
    -inf-logit-masked gold target would produce, since the network could
    never receive a usable gradient signal for a target action whose logit
    the mask always zeroes out at inference/eval time too).

VERDICT (Part A): No bug found in any CE term, the masking logic, or the
teacher-forcing state machine. Every term is computed against the correct
gold target, using exactly the state teacher forcing implies (gold action
history, not the model's own choices), consistently masked the same way
train-side and decode-side. The one item worth a future look (not urgent,
not a correctness bug) is the diluted final-partial-batch gradient noted
in #10, and the fact that ATTACH is fully dead code (item #3).

loss/training path is sound. If OVERALL (or specifically CLOSE_CLAUSE/
STOP) is LOW, that points to a genuine training-path bug, not decode.

FINAL VERDICT
================================================================================
The training/loss path is SOUND. Every CE term in teacher_force_loss is
computed against the correct gold target under exact (leak-free) teacher
forcing; the legality mask is applied identically at train and decode time
and, by construction and by trace, never excludes a gold action; teacher-
forced next-action accuracy is 0.888 overall with STOP=1.000 and
CLOSE_CLAUSE=0.816 (the two terminal actions the pre-fix decode symptom
would have hidden a stopping-learning failure behind, had one existed) --
both comfortably learned, not floor-level. This upper bound is consistent
with the fixed-decode edge-F1 (~0.70, precision=0.700/recall=0.695,
overgen_ratio=1.082, right-sized) via ordinary exposure bias, and the
metric arithmetic itself checks out exactly on a hand-computed example.
The prior extreme over-generation (7.5x, precision=0.11) was a property of
the OLD beam_decode aliasing bug alone, confirmed here by re-decoding the
SAME checkpoint weights with the fix and getting a right-sized forest.
No suspected training/loss bug found.
