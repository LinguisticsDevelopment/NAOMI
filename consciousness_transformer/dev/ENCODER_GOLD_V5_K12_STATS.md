## Time-budget restriction (PILOT -> SCALE-DOWN)

**Pilot**: 400-sentence stratified-by-length sample (seed 0, raw sentences
sampled from the already-deduped corpus, one sentence per block so the
splitter recovers it unchanged) run through the full pipeline,
`--workers 4` (this box's `nproc`). Wall-clock: **114s** for 400 sentences.

**Projection**: linear scale-up at the same worker count,
`114s * (30,690 / 400) ≈ 8,739s ≈ 145.6 min` -- well over the 45-minute
gate. (Caveat worth recording: this likely OVER-projects, because each
worker's one-time USVS-load + parser-construction startup cost is
amortized over only 100 sentences/worker in the pilot vs ~7,700
sentences/worker in a hypothetical full run; the actual v4b-16k build's
measured steady-state rate was 0.204 s/sentence/worker, which would predict
only ~26 min for this corpus. This run followed the task's literal
instruction -- trust the pilot's own measurement, not a borrowed historical
rate -- and restricted accordingly; the real full-corpus run (next ledger
entry) can confirm which estimate was closer.)

**Restriction applied**: a seeded (seed 0) random subset of **81 WHOLE
train-split stories** (so no passage is split mid-story), sized to land
close to a 40-minute budget at the pilot's measured rate
(`400 * 2400/114 ≈ 8,421` sentences target). **val/test were not touched
this run** -- the task's "prefer covering train fully before val/test"
guidance was moot here since even restricting to train-only already
exceeded the time budget (25,802 train sentences alone would project to
~97 min), so the subset is train-only, not "train then spill into val/test".

## Full-build run (this subset)

`GOLD_CORPUS_GLOB` pointed at the 81-story subset (a temp corpus file, not
committed -- the committed `data/corpus/k12_fairytaleqa_train.txt` is the
FULL 25,802-sentence train split; this run only *processed* a subset of
it), `GOLD_OUT_JSONL=runs/encoder_gold_v5_k12.jsonl`, `--workers 4`, default
`CORPUS_MAX_PARSE_SECONDS=10.0` (NOT overridden -- v4b-16k used 30s, see
comparison table note below).

**Wall-clock: 1,825s (30.4 min)**, under the 40-min target and well under
the 45-min gate. Per-worker rate: `1825s / (8420/4) = 1825/2105 ≈ 0.867
s/sentence/worker` (this run's own measured rate, not the historical v4b
rate the projection caveat above cites).

### Comparison to v4b-16k (`dev/ENCODER_GOLD_V4B_16K_STATS.md`)

| metric | v4b-16k (Gutenberg, 16,411 sent.) | v5-k12 (FairytaleQA subset, 8,420 sent.) | delta |
|---|---:|---:|---:|
| yield (ok) | 62.3% | 73.2% | **+10.9pp** |
| no-hypothesis | 28.9% | 19.8% | -9.1pp |
| grounding-fail | 8.2% | 5.8% | -2.4pp |
| cap-hit | 0.6% | 1.3% | +0.7pp |

FairytaleQA's cleaner, simpler grade-school declarative prose parses
noticeably better than 19th-century Gutenberg fairy-tale prose, confirming
`dev/K12_CORPUS_SCOUT.md`'s prediction (94.0% raw parse-yield on its
50-sentence probe vs the Gutenberg baseline's 81.2%; the gap narrows here
because this pipeline's "yield" is full-lattice-record yield, a stricter
bar than the scout's "produced >=1 clause" probe). The slightly higher
cap-hit rate is a parameter difference, not a corpus-difficulty
difference: this run used the pipeline's **default** 10s/sentence cap
(`CORPUS_MAX_PARSE_SECONDS`, unset), while v4b-16k explicitly loosened it
to 30s -- a few FairytaleQA sentences that would have cleared a 30s cap
hit the stricter 10s one instead.

### Holdout coverage

0 sentences were dropped for appearing in `runs/holdout_sentences.txt` (the
98-sentence v4b-16k test split) or `runs/holdout_dev_sentences.txt` (98
sentences, regenerated THIS run via `scripts/make_holdout.py --gold
<fetched encoder-gold-v4b-16k.jsonl> --out-dev runs/holdout_dev_sentences.txt`
-- `--out-test` was pointed at a scratch path so the existing, trustworthy
`holdout_sentences.txt` was never touched/overwritten). This is the
EXPECTED result, not a bug: the two corpora are disjoint sources
(Gutenberg prose vs. FairytaleQA), so zero overlap is what cross-domain
corpora should produce; the exclusion check is a safety net for any future
corpus that *does* share sentences with the held-out eval set, not a
signal of anything found here.

### Known artifact (found and fixed before commit)

The temp subset-extraction script's own `#`-comment header line (not
committed -- an intermediate file only) happened to parse successfully
(the header's descriptive English sentence grounds like ordinary prose),
producing one bogus gold record. Found by inspecting the first record's
`text` field, removed from `runs/encoder_gold_v5_k12.jsonl` before any
stats above were computed (6,161 raw -> 6,160 clean). The same
`#`-header-becomes-a-junk-"sentence" pattern exists in EVERY
`data/corpus/real_gutenberg_*.txt` file already in this repo (their
headers also contain sentence-ending periods) -- an existing, pre-this-run
imperfection in the shared corpus-file convention, not something this
build introduced; flagged here rather than silently worked around upstream
since fixing the shared convention is out of this task's scope.

## Next step

The 81-story train subset above is NOT the full corpus. A follow-up run
(same `GOLD_CORPUS_GLOB='data/corpus/k12_fairytaleqa_*.txt'` the task
specified, no subset restriction) over all 30,690 sentences, with more
wall-clock budget than one routine turn allows, would complete gold v5
proper -- at this run's own measured 0.867 s/sentence/worker rate that is
`30690 * 0.867 / 4 ≈ 6,650s ≈ 111 min`; at the untrusted-but-plausible
v4b-16k historical rate (0.204 s/sentence/worker) it would be `30690 *
0.204 / 4 ≈ 1,565s ≈ 26 min`. Worth re-timing a bigger pilot (e.g. 2,000
sentences) next time to resolve which estimate is closer before committing
to a multi-hour unattended run.
