## v4b-16k: full corpus-expand build (branch `encoder-gold-v4b-16k`)

Same v4b pipeline (`--forest top1` default, POS-aware lemmatization
`dev/ENCODER_GOLD_V4B_SMALL_STATS.md`) run over the FULL corpus-expand
population (`data/corpus/real_*.txt`, all 9 files, 16,411 unique deduped
sentences -- 1,475 -> 16,411, `runs/corpus_expand_report.txt`) instead of
the original 1,475. New in this build: `--workers 4` (added to
`scripts/build_encoder_gold_v2.py` for this run -- shards the sentence
list into 4 contiguous chunks across `fork()`ed subprocesses, each
independently loading USVS + building its own parser and writing its own
JSONL shard, concatenated in original sentence order afterward; verified
byte-identical to `--workers=1` on a 90-sentence sample before the full
run). `OMP_NUM_THREADS=1`, `CORPUS_MAX_PARSE_SECONDS=30` (30s/sentence cap,
not the 10s corpus default and not v4b-small's 60s -- volume mattered more
than the long tail for this build, per the task brief).

**Wall-clock:** 3,343s (55.7 min) for all 16,411 sentences across 4
workers on a 4-core CPU box -- 0.204 s/sentence/worker throughput
(3343s / (16411/4)), close to the 0.19s/sentence the first-500-sentence
timing sample projected (190s/500 sentences x 4 workers -> ~104 min
projected at that sample's slower early mix; the full run finished faster
than the projection because the sample's first 500 sentences (Alice,
front-loaded in `sorted(glob(...))` order) run harder than the corpus
average). Well under the 3-hour drop-to-`--corpus-files` threshold, so the
full 9-file population was kept.

**cap-hits: 101 / 16,411 (0.6%)** -- sentences that hit the 30s
per-sentence parse-time cap (`CORPUS_MAX_HYPOTHESES`/
`CORPUS_MAX_PARSE_SECONDS`, `nsm_ct.corpus`) and were skipped, not
retried at a longer cap. This is the direct cost of the 30s-vs-60s
decision: v4b-small's 60s cap over the original 1,475-sentence population
saw 9 cap-hits (`dev/ENCODER_GOLD_V4B_SMALL_STATS.md`); scaled naively to
16,411 sentences that rate would predict ~100 cap-hits at 60s too, so the
lower 30s cap does not appear to have meaningfully increased the cap-hit
rate over what volume alone would produce -- the long tail this build
intentionally traded away was small.

**Comparison to `dev/CURRENT_STATE.md`'s prior estimate** ("Grimm/Jacobs
parse ~50% vs Burgess 82%", decision D1's corpus-expand rationale, and
`dev/AUDIT_2026-09-08.md`'s "new sources parse at 50% (Grimm/Jacobs) with
26-28%[pt] lower yield"): the actual v4b-16k numbers land close but
consistently a few points ABOVE that earlier estimate -- Grimm 57.5% and
Jacobs 58.8% (vs. the ~50% cited), Burgess-more 80.2% (vs. 82% cited, a
match within noise). The earlier estimate almost certainly came from the
PRE-D1 pipeline (before top-1 forest pruning + POS-aware lemmatization
both landed) or from a smaller probe sample; this build's per-source
yields are the first ones measured with the actual v4b-16k pipeline over
the full population, and they still cleanly reproduce the qualitative
finding that motivated D1's "keep all sources" decision: the two NEW
Grimm/Jacobs sources parse ~20-23pt worse than the original Burgess/Bryant
sources, but a failed parse is lost gold, not noise -- keeping them still
nets +1,634 and +1,591 records respectively that would not otherwise
exist. Alice is the hardest source in the whole corpus (48.3%, below even
Grimm/Jacobs) -- consistent with `dev/K12_CORPUS_SCOUT.md`'s and
`dev/M62_GOLD_VOLUME_PROBE.md`'s general finding that 19th-century
Gutenberg prose's hardest bin is short/fragmentary dialogue-heavy text,
which Carroll's Alice leans into more than the other sources (the M62
probe measured Alice specifically at 75.4% on ITS 138-sentence sample --
pre-expansion, pre-D1 pipeline, so not directly comparable in absolute
terms, but directionally Alice was already the weakest of the 5 original
sources there too).

### `lemma != word` count

**10,096** of the 57,353 sense-grounded nodes (17.6%) have a lemma that
differs from the raw surface word (case-insensitive compare) -- i.e. the
v4b POS-aware morphy path actually changed the surface form for about 1 in
6 sense-grounded nodes (plurals/inflections normalized to their lemma:
`children`->`child`, `appreciate` unchanged, etc; the rest either had no
inflection to strip or are function words that never reach morphy per the
v4b fix).

### `interj.*` count

**4** sense-grounded nodes carry an `interj.*`-namespaced candidate
anywhere in their candidate list (D2's gloss-grounded pure-interjection
senses, `data/usvs` -- these are rare because bare interjections are a
small fraction of declarative children's-lit narrative prose; consistent
with `build_usvs.py`'s own build log for this run, "pure interjections
gloss-grounded (post-fingerprint, additive): 20" senses total available in
USVS, of which only a handful actually appear as a candidate in this
corpus's grounded tokens).

### Holdout coverage

- `runs/holdout_sentences.txt` (98 test-split sentences): **98/98 (100%)**
  covered -- every held-out test sentence has a corresponding `ok` record
  in `encoder_gold_v4b_16k.jsonl`.
- `runs/holdout_dev_sentences.txt`: **does not exist in this repo** (not
  committed on `claude/m27-m28-cleanup`, `encoder-gold-v4b-variants`, or
  anywhere else in git history). `scripts/make_holdout.py`'s own docstring
  says it should be regenerated FROM `runs/encoder_gold_v2.jsonl` (the
  original, pre-D1 candidate-lattice gold, seed=0, n_train=788, n_dev=98,
  n_test=98) -- that file is itself gitignored and was never committed
  anywhere reachable from this branch, so the exact dev split cannot be
  reconstructed here. Regenerating `scripts/make_holdout.py` against the
  nearest available substitute (`runs/encoder_gold_v4b_small.jsonl`, 987
  records, same seed/split sizes) produces a COMPLETELY DIFFERENT 98-
  sentence set from the committed `holdout_sentences.txt` (verified by
  diff -- zero overlap in a spot check), because `stratified_split`
  buckets by forest width (1 tree / 2-3 trees / 4+ trees) and v4b's
  `--forest top1` default collapses every record to 1 tree, while the
  original split was drawn from a build with forest width averaging 3.46
  trees/sentence (pre-D1) -- the stratification itself is unrecoverable
  without the original file, not just the split's random draw. **This is
  a real gap, not silently patched**: no `holdout_dev_sentences.txt` is
  committed by this build. Whoever regenerates or locates the true
  `encoder_gold_v2.jsonl` can run `scripts/make_holdout.py --gold
  runs/encoder_gold_v2.jsonl` to produce the authentic dev split; until
  then, `holdout_sentences.txt` (verified 98/98 covered here) remains the
  one trustworthy held-out set for arm comparisons.
